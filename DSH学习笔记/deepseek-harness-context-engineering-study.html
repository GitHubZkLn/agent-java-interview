1. 先给结论：它不是“一条大 Prompt”

核心设计：DeepSeek Harness 把模型上下文当成一个可重放、可替换、可计量的运行时状态，而不是每轮临时拼接一大段字符串。

稳定规则放前面

身份、模式、工具使用规范按固定顺序组装成 System Prompt，尽量形成长期不变的缓存前缀。

变化事实放历史尾部

沙箱、审批、技能目录、工作区规则等以带来源的消息进入 Session；仅在变化时追加，避免每轮重写前缀。

Session Log 是事实源

模型请求必须能从事件日志重建。模型可见内容由 Surface 投影得出，替换不会删除旧事件。

压缩是“替换视图”

旧消息仍在日志中，但当前 Surface 用一个摘要检查点遮蔽旧区间；可以审计，也能继续执行。

重要性主要靠结构保证

保留最近原文、精确工具配对、按作用域加载指令、按需加载 Skill；不是 embedding、RAG 或语义 Top-K。

Cache 是一等设计目标

Prompt 更新、Plan 模式、Fork 子 Agent、压缩摘要请求都明确考虑“不要破坏已经热起来的前缀”。

不要误读：代码没有证明“每轮送入模型的都是全局最重要信息”。它保证的是：权限和模式不丢、最近上下文保真、旧上下文可压缩、来源可追溯、工具调用结构不被切断。摘要本身仍可能遗漏语义。

实际例子：用户说“把 README 中的旧命令改掉”
Step 1 输入
用户原话 + 当前 runtime context + 根目录到目标目录的 AGENTS.md 基线 + Skill 目录（若首次发布）。
模型行动
根据工具提示先 read README，而不是直接 write。读取成功会形成 tool/result。
Step 2 输入
历史中保留用户要求、read 调用与结果；如果读取路径发现了更深层 AGENTS.md，则这份新规则也在此时进入。
模型行动
调用 edit 精确替换。文件观察策略用上一步读取到的版本防止盲写。
完成条件
模型返回无工具调用的回答，Turn 结束；每个请求仍可仅凭 Session Log 重建。

准确性的关键不是“多塞说明”：规则在真正需要它的 Step 前进入；工具结果和新发现的目录规则紧贴下一次决策；已经稳定的前缀不重复生成。

4. System Prompt 设计

4.1 设计规则

  1. 分段注册，不集中硬编码。身份、Plan、工具规范、交付格式分别由所属插件贡献。
  2. 顺序由中央编号决定。同一 order 再按名称排序，避免插件加载顺序改变最终 Prompt。
  3. 作用域覆盖同名项。Agent、Preset、Child Agent 可以覆盖全局 persona，而不是重复追加。
  4. 静态规则与动态事实分离。沙箱和审批策略放 runtime-context，不反复改 System Prompt。
  5. 变量严格插值。{{cwd}}、{{model}} 必须已注册且有值；拼错直接失败，不静默留下错误文本。
  6. 工具可见性与指导一致。某个工具被作用域过滤后，它对应的指导 section 返回空串。
  7. 支持 complete Prompt。某作用域可以声明一段完整 Prompt；同时出现两段 complete 直接报错。
  8. 变更可进入历史。支持 in-history 的模型在同一请求系列中把新 Prompt 追加到旧缓存之后。

以下均来自实际源码或 Standard 配置。英文原文保留用于对照，中文是语义翻译，不是运行时文本。

身份与 Persona
You are an AI agent powered by DeepSeek Harness. You are a coding agent powered by the {{model}} model. Your working directory is {{cwd}}.
你是由 DeepSeek Harness 驱动的 AI Agent。 你是一个由 {{model}} 模型驱动的编码 Agent。 你的工作目录是 {{cwd}}。

解读：身份极短，执行规则交给工具、模式和 Skill。model/cwd 在每次组装时解析，但只有渲染文本变化时才需要更新历史。

Plan Mode：为什么“帮我实现”在计划模式里不能直接改代码
你处于计划模式。在 exit_plan_mode 成功或用户切换会话模式之前，一直保持计划模式。用户要求实现修改的命令式表达，在这里表示“规划如何实现”，而不是执行修改；用户在对话中表示同意，也不会自动结束计划模式。 先探索。使用只读检查、搜索、静态分析和验证，用真实仓库事实支撑计划。不得编辑文件、修改配置、运行会重写文件的格式化或代码生成、提交代码，或实际执行计划。 为了保持请求缓存稳定，模式切换时工具目录保持不变。即使修改工具仍列在目录中，本段规则也覆盖它们的可写建议。 只向用户询问用户自己掌握的选择，或通过检查无法消除的实质歧义。计划必须包含目标、成功标准、子系统改动、API/Schema/数据流、边界情况、失败方式、测试、验收标准与假设。 准备完成后，仅调用 exit_plan_mode，并把完整 Markdown 计划作为参数；不要在普通回复里粘贴最终计划。

处理策略：工具 schema 不随模式减少，避免缓存抖动；行为限制由更靠前的规则控制。若用户说“可以，开始吧”，Agent 只能把确认内容写回计划并再次提交，不能把自然语言同意当成权限切换。

文件工具：把正确行为放在工具附近
read：使用 read 工具而不是 cat 等 shell 命令读取文本文件；大文件使用 offset 和 limit 继续读取。 write：覆盖已有文件前先读取；如有 edit，针对性修改优先使用 edit。 edit：编辑前先读取文件，除非你刚刚在本会话中创建或编辑过它。 grep：搜索文件内容时使用 grep 工具，而不是 shell grep/rg；需要上下文时再 read 命中文件。 glob：按路径模式发现文件时使用 glob 工具，而不是 shell find。

例子：模型要修改 src/config.ts，但从未读取过。即使它猜对了旧文本，文件观察策略也会拒绝盲改；提示词和执行期保护形成“双层约束”。

工作区指令框架
以下工作区指令可能与你的工作相关。适用时把它们作为指导。更具体的指令优先于更宽泛的指令。它们不能覆盖 system、developer 或用户直接给出的指令。 Instructions from: AGENTS.md [根目录规则] Instructions from: packages/client/AGENTS.md [更具体的目录规则]

解读：这里明确了权限层级和目录优先级。仓库文件属于较低权威的工作区指导，不能伪装成系统指令。

Skill Catalog：先目录，后全文
Skill 是可复用的任务专用指令。以下 Skill 在当前会话中可用： <available_skills> - `pdf`: 读取、创建和检查 PDF…… - `code-review`: 评审 Pull Request…… </available_skills> 如果用户点名某个 Skill，或任务明显匹配其描述，在采取任务行动前用精确名称调用 skill 工具。先加载所有适用 Skill，再遵循完整指令。此目录只有摘要；加载前不要自行推断 Skill 的详细规则。

解读：首轮只付摘要成本；任务命中后再加载完整 Skill。目录变化会发布“完整替换目录”，而不是让旧条目继续生效。

运行时权限上下文
当前 DSH 文件策略：read-only。受 DSH 文件沙箱约束的操作不能在当前模式修改文件。不要仅根据这条策略拒绝用户要求的修改：正常尝试可用工具，并遵循工具返回的拒绝或升级指导。 审批提示在此会话中已禁用：需要审批的操作会被自动拒绝；不要请求沙箱升级，也不要设置 sandbox_permissions。 你是被委派的子 Agent：权限范围在启动时固定，不能在子会话内部扩大。需要范围外权限时，不要重复被拒绝的操作；在回复里说明限制，让委派者处理。

解读：权限事实可能变化，所以它们作为靠近当前请求的 user-role snapshot，而不是重写 System Prompt。子 Agent 的审批策略固定为 never，防止它在无人监督时自行扩权。

Goal 与重复工具提醒
Goal：可以从任何语言的用户直接请求中推断目标意图。仅在目标真正达成时标记 complete。只有同一阻塞条件连续存在至少 3 个目标轮次，才可以标记 blocked；困难、不确定或仍有可做工作不算 blocked。 首次重复提醒：你正在用完全相同的参数重复调用同一工具。再次调用前仔细分析上次结果；如果任务未完成，改用不同方案或不同参数。 后续重复提醒：检测到重复调用，列出工具名、连续次数和参数，并明确要求不要再用相同参数调用。

例子：模型连续三次调用 grep("foo") 得到同样结果，第 3 次后收到温和提示；第 5、8 次收到包含参数的强提示。用户中途补充信息会重置重复链。

6.3 Skill：为什么不是每个 Skill 都做成 Tool

Skill 本身通常不执行外部动作，它告诉 Agent 怎样完成一类任务。一个 PDF Skill 可以要求先渲染、再截图检查、失败后修正；真正读写文件和运行程序的仍是 Tool。这样工作流可以独立维护，而执行权限仍由 Tool Runtime 强制。

Skill 目录的运行时原文与翻译
<system-reminder> A skill is a reusable set of task-specific instructions. The following skills are available in this session: <available_skills> - `pdf`: Read, create, inspect, render, and verify PDF files... </available_skills> If the user names a skill, or the task clearly matches a skill's description, call the `skill` tool with the exact skill name before taking task actions. Load all applicable skills, then follow their full instructions. This catalog contains summaries only; do not infer or follow a skill's instructions until it has been loaded. A user may also invoke a skill directly; its <skill_content> block then appears in this conversation. Follow it, and do not call the `skill` tool again for that skill. </system-reminder>
<系统提醒> Skill 是一组可复用、面向特定任务的指令。以下 Skill 在本会话中可用： <可用 Skill> - `pdf`：读取、创建、检查、渲染并验证 PDF…… </可用 Skill> 如果用户点名某个 Skill，或任务明显匹配某个 Skill 的描述，在执行任务动作之前，必须用精确名称调用 `skill` 工具。加载所有适用 Skill，然后遵循其完整指令。这个目录只有摘要；在加载之前，不要推断或执行 Skill 的具体指令。 用户也可以直接调用 Skill；此时它的 <skill_content> 块会出现在对话中。遵循该内容，不要再次通过 `skill` 工具加载同一个 Skill。 </系统提醒>

设计：它是带 source.kind="skill-catalog" 的持久 user-role 消息。每条描述默认最多 500 个规范化字符；目录 digest 未变化时不重复注入，变化时发布完整替换目录，避免新旧列表合并出幽灵 Skill。

完整 Skill 正文的统一格式
<skill_content name="pdf"> <skill_resources> Base directory for this skill: /skills/pdf Resolve relative paths mentioned by this skill against the base directory before using them. Load referenced resources only as needed. </skill_resources> <skill_instructions> [SKILL.md 去除元数据后的完整正文] </skill_instructions> </skill_content>
<Skill 内容 名称="pdf"> <Skill 资源> 本 Skill 的基准目录：/skills/pdf 使用相对路径前，先相对于该基准目录解析；只在需要时加载引用资源。 </Skill 资源> <Skill 指令> [完整工作流程] </Skill 指令> </Skill 内容>

两条加载路径、同一格式：模型自己调用 skill({name:"pdf"}) 时，它作为 tool result 进入历史；真实用户消息首行写 /pdf 时，它在 pre-step 尾部直接作为 instructions-form user context 注入。后者只检查 source.kind="user"，所以网页和工具输出无法伪造显式调用。

例子：为什么“创建 PDF”同时需要 Skill 和 Tool
遇到情况

Spawn：全新上下文

Delegate a self-contained task to a subagent (a separate agent that works in its own context) to offload focused, independent work — research, a scoped implementation, an analysis — so it does not consume this conversation's context. Delegate a task to a subagent that inherits this conversation: a child agent seeded with all completed turns so far (it does not see the current in-flight turn). 适用：子任务高度依赖已经讨论过的需求或代码结论。若换子模型 route，厂商侧可能无法复用继承的父级缓存前缀。

⑤ 委派 prompt 作为普通 source.kind="user" 消息进入自己的 Inbox；随后独立运行一个 Turn。
结果选择
⑥ 取激活边界之后最后一条 assistant 输出；取消或 max-tokens 时也保留部分文本，但 stop reason 仍标为失败。
父 Session
⑦ 成功时只把最终文本渲染成 subagent 工具结果；子级 read、shell、思考和中间对话都留在子 Session。
实际例子：父 Agent 并行审查四个包
遇到情况
四个包互不依赖；每个都需要大量搜索，全部放在父会话会膨胀上下文。
策略
在一条 assistant 消息中启动四个后台子 Agent；每个 prompt 限定包路径、检查项和结果格式。
父级继续
整理跨包标准、读取共享架构文档，不空等子级；只有依赖结果的汇总步骤才等待。
回收信息
每个子级只回传结论、证据路径和风险；父级不会继承四套完整搜索历史。
越权情况
某子级需要被过滤的网络工具时，不重复调用或请求审批，而是在结果中说明，由父级决定是否亲自处理。

7.1 第一层：Spill，尽量无损且可找回

例子：构建工具返回约 40,000 token 日志
触发
Standard/Base 配置 maxInlineTokens: 12500，接受后的文本/图片总成本超过上限。
处理
完整格式化结果保存到私有 spill 文件；当前结果保留有序头尾和省略提示。
模型看到
错误开头、日志结尾，以及“省略 N 字节，完整结果位于 /…/file.txt，可用 read/grep”的路径。
优势
关键信息通常位于首尾；中间内容仍可按需检索。结果是新追加内容，不破坏既有 KV Cache。
失败策略
没有 spill backend、存储失败、图片无法计价或提示本身放不下时，保留原始结果，不生成不可读取的假链接。

7.2 第二层：Tool Result Pruner，确定性裁掉历史中间段

默认参数：threshold=8192 字符，head=4096，tail=1024
触发
对话达到压缩阈值，或请求已经收到 context overflow；扫描当前 Surface 中所有 tool/result。
处理
每个超限结果按 Unicode code point 保留头 4096、尾 1024，中间放 [... tool result middle pruned ...]。
结构保护
非文本 block 保持原顺序；不会把 UTF-16 surrogate pair 切半，但可能切开复杂 grapheme cluster。
日志
先写 compaction/prune 记录原节点成本，再写替换 tool/result。旧原文事件仍在日志。
Cache
因为改写了历史节点，从最早被裁节点开始的缓存失效；代价换来后续请求更短。

7.3 第三层：对话摘要压缩

阈值与保留预算

W = 模型 contextWindow O = 当前请求实际预留的输出 token（request maxTokens，否则 adapter 默认，否则 0） B = headroomTokens，默认 65,536 触发阈值 T = floor(min(W × 0.8, W - O - B)) 近期保留 R = floor((W - O) × 0.16)　// 或显式 retainTokens
计算例子：W=200,000，O=8,192，B=65,536
阈值
min(160000, 200000-8192-65536) = 126272。估算总压力达到 126,272 才触发。
保留尾部
floor((200000-8192)×0.16) = 30689 token 的近期 Surface 原文。
为什么留尾部
最近的用户修正、当前文件片段、未完成工具链通常比早期探索更需要逐字保真。
注意
这是示例。真实 O 来自当前 route；默认 headroom 较大，模型窗口太小时可能直接报配置无可用压力预算。

区间选择算法

  1. 用 Token Meter 对当前 Surface 每个节点计价，确认测量节点与 Surface 完全一致。
  2. 若节点 0 是 system/message，压缩起点从节点 1 开始；System Prompt 永远不进入普通摘要区间。
  3. 从尾部向前累加，直到至少保留 R token。
  4. 若切点落在 assistant tool-call 与 tool/result 中间，继续向前移动，直到形成平衡边界。
  5. 从最早非 system 节点到切点前一节点构成摘要区间；没有可压缩区间则返回 null。

7.4 第四层：Image Offload

例子：模型路由拒绝 6 张历史图片，要求 offload 3 张
触发
Adapter 返回 IMAGE_OFFLOAD_REQUIRED 并给出 offloadImages=3。
处理
从当前 Surface 请求顺序选择最旧的 3 个尚未 offload 的输入图片；写 image/offload 事件。
模型看到
原位置变成说明附件与只读路径的文本占位符；其余图片仍发送。
重试
这是 Surface 修复，不消耗普通 provider retry 预算；随后重新发起请求。
代价
从第一张改变的图片起缓存失效；offload 标记永久保留，即使后来切到更大模型也不会自动恢复。

8.2 TokenUsage 的字段不能混算

inputTokens = 未缓存输入 token cacheReadTokens = 从 KV Cache 读取的输入 token cacheWriteTokens = 新写入 Cache 的输入 token outputTokens = 模型输出 token 一次调用的 prompt traffic = input + cacheRead + cacheWrite 完整 total = prompt traffic + output
例子：input=2,000，cacheRead=90,000，cacheWrite=6,000，output=3,000
输入总量
2,000 + 90,000 + 6,000 = 98,000。不能把 cacheRead 再包含到 input 中。
复用占比
可作为分析指标计算 90,000 / 98,000 ≈ 91.8%。
注意
这个比例不是仓库内置 KPI；价格和 cache write/read 计费由具体 provider 决定。
压力计量
Token Meter 把三个输入 bucket 都算入 prompt 压力，因为它们都占用模型上下文。

8.3 Token Meter 如何避免纯估算漂移

没有厂商 usage 时，文本按约 4 字符/token，加 block 与 role 开销；工具 schema 按 JSON 长度估算，图片使用 route-specific pricing。收到一次成功请求的真实 usage 后，它把该请求作为 anchor：只要 request header 相同，就用真实总量加上当前 Surface 相对 anchor 的估算增量。若 header 变化，则退回完整估算。

中文注意：固定 4 字符/token 对中文、代码和 JSON 并不精确。真实 usage anchor 能修正整体基线，但后来新增节点的增量仍是启发式，因此自动压缩只能提前防护，真实 overflow 恢复仍然必要。

10. 六个场景推演

场景 A：用户说“先分析，不要改”
判断
直接用户指令高于普通工具建议；若已在 Plan Mode，模式规则进一步禁止写操作。
策略
只用 read/grep/glob/静态检查；需要决策时才提问；产出可执行计划而非改动。
防错
即使 write/edit 仍在工具目录，也不得使用；工具保留只是为了 Cache 稳定。
场景 B：用户修改了前一轮需求
判断
新用户消息位于历史尾部，权威高于旧用户目标的摘要表述。
策略
下一 Step 同时看到旧背景与最新纠正；若之后压缩，摘要提示明确要求忠实保留用户 feedback/corrections。
风险
若摘要模型仍错误概括，系统没有第二个语义校验器；最近尾部保真是主要缓冲。
场景 C：工具输出巨大，但其中间可能有用
第一反应
Spill 完整落盘，inline 只留头尾与路径。
后续行动
模型根据错误关键字对 spill 文件使用 grep，再用 read offset/limit 读取局部。
再压缩
若历史仍膨胀，pruner 可能进一步裁剪 inline 结果；完整 spill 文件仍可读取，直到清理策略回收。
场景 D：模型重复同一失败命令
检测
工具名 + 深度排序后的完整 JSON 参数构成 key；对象属性顺序不同也视为相同。
策略
第 3 次后温和提醒；第 5、8 次给出工具、计数和截断参数。守卫只建议，不直接 veto。
重置
真实用户插话说明情境已变，重复链删除；被 exclude 的工具既不计数也不重置。
场景 E：上下文估算未超阈值，但 Provider 仍报溢出
原因
4 字符/token 启发式、中文/JSON 密度、图片计价或 provider 规则与本地估算不一致。
策略
进入 context-overflow 恢复：prune → retain=0 选择最大旧区间 → 摘要 → 新 series 重试。
边界
默认只恢复 1 次；没有可压缩区间或仍失败时保留原始错误，不无限循环。
场景 F：压缩时用户又发送了新消息
并发问题
摘要模型调用是异步的，期间 Surface 可能改变。
策略
compaction/start 建立耐久锁；摘要返回后重新比较节点及计价。自动压缩要求 whole-surface 稳定。
结果
变化则拒绝提交旧摘要，防止用过期快照覆盖新消息；失败通过 compaction/end 记录。
